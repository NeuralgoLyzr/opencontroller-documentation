description: "Make every LLM gateway call carry the Auth0 user behind it, so guardrail violations name the person, not only the key."
icon: "fingerprint"
---

A virtual key says which app called the LLM gateway (Rekori), not which person. With caller identity, the app also sends
the signed-in user's Auth0 access token on each call. The gateway verifies it and records a claim from it as the caller,
and a key that requires sign-in refuses every call without a valid token, so a leaked key alone is not enough.

The caller shows in [Guardrail Violations](/secure/who-trips/violations) **By caller**. The **Logs** page does not show
it: its **Caller** column is the key and its team or customer.

It needs the **LLM Gateway** module and the **Admin** role. For signing in to the console, see
[Any OpenID Connect provider](/integrations/identity/oidc).

## Set up Auth0 for gateway callers

<Steps>
  <Step title="Create an API in Auth0">
    In the Auth0 Dashboard, go to **Applications** > **APIs** > **Create API**. Set **Identifier** to a name for the
    gateway, for example `https://rekori`; it is the tokens' **audience**, and cannot be changed later. Keep the signing
    algorithm **RS256**: the gateway refuses HS256.

    Auth0 issues a JWT access token only when the app asks for this audience. Without it, the token is opaque and the
    gateway refuses it.
  </Step>
  <Step title="Authorize the application">
    Use the Auth0 application your users sign in to. Under **Settings** > **Advanced Settings** > **Grant Types**, turn on
    the grant it uses: **Authorization Code** for a web app, or **Password** to test from a script. Then open the API >
    **Application Access**, and authorize the application for **User Access**.

    For the **Password** grant, also set **Settings** > **General** > **API Authorization Settings** > **Default
    Directory** to `Username-Password-Authentication`. Without it, Auth0 answers "Authorization server not configured
    with default connection".
  </Step>
  <Step title="Put the email in the token">
    The token's `sub` is an Auth0 user ID such as `auth0|64f1c2…`. To see emails, add one with an Action: **Actions** >
    **Library** > **Create Action** > **Build from scratch**, trigger **Login / Post Login**:

    ```js
    exports.onExecutePostLogin = async (event, api) => {
      // A namespaced claim: Auth0 drops custom claims without a namespace.
      api.accessToken.setCustomClaim("https://opencontroller.sh/email", event.user.email);
    };
    ```

    Select **Deploy**, then add it to the **Post Login** trigger under **Actions** > **Triggers**.
  </Step>
  <Step title="Add Auth0 as an identity provider in the gateway">
    In OpenController, go to **LLM Gateway** > **Routing** > **Identity providers** > **New identity provider**:

    | Field | What to enter |
    |---|---|
    | **Name** | `auth0`. It cannot be changed later. |
    | **Issuer** | `https://your-tenant.us.auth0.com/`. Must match the token's `iss`; a trailing slash is ignored. |
    | **JWKS URL** | `https://your-tenant.us.auth0.com/.well-known/jwks.json`. Fill it in: when empty it is looked up from the issuer, and if that lookup fails, no identity provider loads, though the save reports success. |
    | **Audiences** | `https://rekori`, the API's identifier. Separate several with commas. |
    | **Subject claim** | `https://opencontroller.sh/email`, or empty for `sub`. If the token lacks the claim you name, the caller is empty: it does not fall back to `sub`. |
    | **Enabled** | On |

    Leave the rest empty: **Algorithms** (RS, ES and EdDSA; never HS or `none`), **Clock leeway (seconds)** (30),
    **Scopes claim**, **Roles claim**, **Teams claim**, and **Client ID** and **Scopes**, which are not used to verify
    tokens. Select **Create**.
  </Step>
  <Step title="Require sign-in on the virtual key">
    Go to **LLM Gateway** > **Virtual Keys**, open the key's actions menu (**…**) > **Edit** (or **New key**). Under
    **Callers sign in with**, switch on **auth0**, and select **Save** (or **Create**).

    <Warning>
    From then on, every call with this key needs a valid token from a provider switched on for it. Calls with the key
    alone are refused. Update the app first, or test with a new key. A key with no provider switched on ignores tokens:
    they are neither checked nor recorded.
    </Warning>
  </Step>
  <Step title="Call the gateway with the key and the token">
    Send the virtual key in `x-bf-vk` and the user's access token as the bearer token. Sending the key as the bearer
    leaves no room for the token, and the call is refused.

    ```bash
    curl https://<gateway address>/v1/chat/completions \
      -H "x-bf-vk: sk-bf-…abcd" \
      -H "Authorization: Bearer $ACCESS_TOKEN" \
      -H "Content-Type: application/json" \
      -d '{"model": "openai/gpt-4o-mini", "messages": [{"role": "user", "content": "Hello"}]}'
    ```

    To get a test token with the Password grant:

    ```bash
    curl -s https://your-tenant.us.auth0.com/oauth/token \
      -H "Content-Type: application/json" \
      -d '{"grant_type": "password", "username": "alice@example.com", "password": "<password>",
           "audience": "https://rekori", "client_id": "<client id>", "client_secret": "<client secret>",
           "scope": "openid email"}'
    ```

    A call with the key and a valid token succeeds. Without the token it is refused with `401
    identity_token_required`; with a bad one, `401 identity_token_invalid`.
  </Step>
</Steps>

## What it checks

| Check | Rule |
|---|---|
| Format | A signed JWT, at most 16 KiB. An opaque token is refused. |
| Signature | Against the provider's JWKS, by the token's `kid`. Algorithms: RS256/384/512, ES256/384/512, EdDSA. |
| Issuer | `iss` matches **Issuer** (trailing slash ignored, otherwise exact). |
| Audience | One of **Audiences** is in `aud`. With **Audiences** empty, audience is not checked. |
| Time | `exp` required; `exp` and `nbf` checked with 30 seconds' leeway. |

The token is never stored; the subject is, as the call's user.

<Warning>
- **Anyone with a valid token for the audience** can use the key: any user of any application authorized for the API.
  Authorize only the applications that should call the gateway.
- **Passthrough routes forward the token.** On `/v1`, `Authorization` never goes upstream. On `/openai_passthrough`
  and `/chatgpt_passthrough`, a JWT bearer is forwarded to OpenAI over https in place of the stored provider key. Use
  `/v1` routes with caller identity.
- **No replay protection.** A token works until it expires: keep Auth0's access token lifetime short.
- **Key rotation.** The JWKS is fetched again only when a token arrives with an unknown `kid`. A signing key revoked in
  Auth0 stays trusted until then.
- **The subject is personal data** if it is an email: it is stored with each call and violation, and is a label on the
  gateway's metrics.
- **Disabling the provider** makes every key that requires it refuse all calls.
</Warning>
