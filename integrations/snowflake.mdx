OpenController reads a Snowflake account as a **service user** whose role sees what the account holds and reads none
of its data. One integration is one account. It uses up to two users:

- **The read user** (required): discovery and Verify sign in as it. Its role changes nothing.
- **The control user** (optional): changes OpenController makes are made as it. Its role manages grants on the account.

Each user signs in one of two ways:

- **Workload identity federation** (recommended): the user trusts OpenController's own AWS identity. No secret exists.
- **Key pair**: OpenController generates an RSA key. The private half goes straight into your secrets manager and is
  never shown; the setup script sets the public half on the user. Use it where OpenController has no AWS identity, such
  as a trial.

## What it unlocks

- **[AI Inventory](/discover/ai-inventory):** Cortex Agents with their models, tools, skills and instructions
  (credentials masked); the CoWork object (formerly Snowflake Intelligence) and the agents it shows; Snowflake-managed and
  external MCP servers; Cortex Search services; semantic views; Model Registry models; the Cortex AI Gateway, the
  models it lets through and whether it logs requests.
- **Usage**, with a warehouse: how much each agent, search service, model, AI function and the gateway was used over
  the last 30 days, on the asset's page. See [Read usage and spend](#read-usage-and-spend-optional).
- **[Spend](/discover/people-and-spend)**, with a warehouse: the AI credits the account was billed each day, priced,
  and whose they were, by user and by agent.
- **[Shadow AI](/discover/shadow-ai):** the owner role of each agent and MCP server, the roles and users that
  can use or edit it, and whether `PUBLIC` holds it (exposure to the whole account), and whether every user may send
  inference through the AI Gateway.
- **Control (optional):** share agents and MCP servers with roles and users, end access for everyone, publish to
  CoWork, and block an agent.

Neither user ever reads your table data, calls an agent, a search service, an MCP tool or an AI function, or reads
conversations, traces or files users upload to CoWork.

## Connect a Snowflake account

<Steps>
  <Step title="Connect it">
    Go to **Integrations** > **Connect** > **Snowflake account**. Fill in:

    | Field | What to enter |
    |---|---|
    | **Name** | A name for the account, for example `analytics`. |
    | **Account identifier** | `orgname-account_name`, for example `myorg-myaccount`. In Snowsight: your name (bottom left) > **Account** > **View account details**. |
    | **Warehouse** (optional) | A warehouse the account usage views are read on, for usage and spend, and for blocking agents, for example `OPENCONTROLLER_WH`. The setup script creates it. Listing objects needs none. You can add it later, under **Usage and spend** on the account's row. |
    | **Credit price** and **Currency** (optional) | What the account pays for one Snowflake credit, from your contract, to price AI usage. Without one, spend reads the organization's rate sheet. You can set it later, under **Usage and spend** on the account's row. |
    | **Read user** | Keep `OPENCONTROLLER_READ`, or enter another name. |
    | **Read user: signs in with** | **Workload identity federation (recommended)** or **Key pair**. The form starts on **Key pair**. |
    | **Control user** | **None: discovery only** for now. See [Turn on control](#turn-on-control-optional). |

    Select **Connect**. The **Let analytics into Snowflake** dialog opens with a setup script made for this
    connection, with a key-pair user's public key already in it.
  </Step>
  <Step title="Run the setup script in Snowflake">
    Copy the script and run it in a Snowsight worksheet as **ACCOUNTADMIN**: it changes an account setting and creates
    users, roles and a warehouse. What it grants is under [Permissions it uses](#permissions-it-uses).
  </Step>
  <Step title="Verify">
    Select **Done**, then **Verify** on the row. The **Access** badge reads **Verified** when every check passes, or how
    many were refused; without a warehouse it shows **1 refused** (**Account usage**).

    | Check | Passes when |
    |---|---|
    | **Sign in** | The user signs in, and lands in the connection's own account. |
    | **One role** | It acts as its own role alone, with no secondary roles. |
    | **Read only** | Its role is not an administrator role, none of its grants changes anything, and it holds no other role. |
    | **Agents**, **MCP servers**, **Cortex Search**, **Semantic views** | They are listed; the check shows how many. |
    | **CoWork** | Shows how many agents the CoWork object holds, or that there is none. |
    | **Inherited grants** | Says whether one set of grants covers every database. It never fails. |
    | **Account usage** | The warehouse reads `SNOWFLAKE.ACCOUNT_USAGE.CORTEX_AGENT_USAGE_HISTORY`. **not set up** without a warehouse. |
    | **AI Gateway** | The read role holds `MONITOR` on the Cortex AI Gateway, to read what goes through it. A note, not a failure, without it or on an account with no gateway. |

    <Note>In a large account, Snowflake can take longer to list agents, search services or semantic views than Verify
    waits (8 seconds for each check). That check then shows a clock and *not counted*, and the badge reads **1 not
    finished**: it is not a missing grant. The scan waits longer and reads them. Select **Verify** again, or
    **Run scan**.</Note>

    With control on, Verify also runs **Control sign in**, **Control one role**, **Control scope** (`MANAGE GRANTS` on
    the account), **Control CoWork** (`MODIFY` on the CoWork object) and **Control block state** (rights on the block
    table).

    Scans run every 5 minutes by default. Nine sources are read per account, named `snowflake:<account>:global:<family>`:
    `cortex.agents`, `cowork`, `mcp.servers`, `mcp.external`, `cortex.search`, `semantic.views`, `models`, `ai.gateway`
    and `usage`. All but `usage` use `SHOW` and `DESCRIBE`, which need no warehouse. An account without the Cortex AI
    Gateway, a preview feature in some regions, shows `ai.gateway` as **skipped**.
  </Step>
</Steps>

Every statement OpenController runs carries the query tag `opencontroller`, and runs as the users you created for it,
so your own query history shows exactly what was run.

## Turn on control (optional)

On the connect form, set **Control user** to **A user of its own (recommended)**, keep `OPENCONTROLLER_CONTROL`, and
choose **Control user: signs in with**; or select **Turn on** next to **Control: off** on a connected account's row.
Then run the setup script again, from the **Setup** icon on the row.

<Warning>
The control role holds `MANAGE GRANTS` on the account. It can share and unshare any agent or MCP server, a block takes
an agent from its owner role, and `MANAGE GRANTS` would let it grant itself anything. That is close to SECURITYADMIN's
power. It changes grants, never your data.
</Warning>

| Action | Cortex Agent | MCP server | What runs |
|---|---|---|---|
| **Share** (can use, can edit) | Yes | Can use only | `GRANT USAGE` (or `MODIFY`) on the object to a role or user |
| **Remove** | Yes | Yes | `REVOKE` each privilege the role or user holds on it. Not for the owner role, OpenController's own users and roles, or inherited grants. |
| **End access for everyone** | Yes | Yes | `REVOKE … FROM ROLE PUBLIC` |
| **Publish** | Yes | No | `ALTER SNOWFLAKE INTELLIGENCE … ADD AGENT`, adding the agent to CoWork |
| **Block** | Yes | No | Records the agent's grants, takes ownership (`GRANT OWNERSHIP … COPY CURRENT GRANTS`), tags the agent with its owner, and revokes every grant except `OWNERSHIP` and `MONITOR` |
| **Unblock** | Yes | No | Gives back the recorded grants and ownership. Grants to roles dropped since are skipped; with no record left, only ownership comes back. |

A block keeps what it took in your own account (`OPENCONTROLLER.STATE.BLOCK_SNAPSHOTS` and the
`OPENCONTROLLER.STATE.BLOCK_OWNER` tag), never in OpenController. It needs the connection's warehouse.

## Read usage and spend (optional)

With a warehouse on the connection, OpenController reads the account usage views on it. The read role needs `USAGE`
on the warehouse and the `SNOWFLAKE.USAGE_VIEWER` database role, which the setup script grants. Without a warehouse,
the `usage` scan source and spend both show **not set up**, and the objects are listed without their use. To add a
warehouse to a connection that has none, name it under **Usage and spend** on the account's row, then run the setup
script again (**Setup** on the row): it creates the warehouse and lets the read role use it.

### Usage

Once an hour, the `usage` source reads how much each object was used over the last 30 days, and every scan in
between describes the objects with that reading:

| Asset | What its page shows |
|---|---|
| Cortex Agent | Calls, people, tokens and credits (`runs_30d`, `users_30d`, `tokens_30d`, `credits_30d`), the interfaces it was called from, and when it was last used. Calls made through CoWork count in the credits, not the calls. |
| CoWork | Its credits and people. |
| Cortex Search service | Its credits, split into serving, embedding and batch. |
| Model | Credits, queries and people through AI functions such as `AI_COMPLETE`, and requests, people and tokens sent straight to the Cortex REST API (`api_requests_30d`, `api_users_30d`, `api_tokens_30d`). A model only the API calls is listed too. |
| AI function and Cortex Code | Each AI function and each Cortex Code interface, with its credits and people. |
| Cortex AI Gateway | Credits and people over 30 days, and the requests, people, credits and models over the year the view keeps (`requests_365d`, `users_365d`, `credits_365d`, `models_365d`). This part needs `MONITOR` on the gateway; without it the gateway shows `usage_error`. |

Each reading runs seven queries on the warehouse and spends its credits. The views lag Snowflake by up to an hour.

### Spend

Every 6 hours by default (**Settings** > **Spend schedule**), spend reads the last 35 days of AI credits:

- **What was billed**, each day by service: Cortex Agents, CoWork, Cortex Code, AI functions, AI Gateway inference,
  Cortex Search and the other Cortex AI services, from `METERING_DAILY_HISTORY`.
- **Whose it was**: each user's credits per service and, for agents, per agent, from `USER_AI_USAGE_HISTORY`. These
  rows are **attributed** under the totals, so the totals count once. **People** says who spent what, an agent's
  rows show on the agent's page, and the gateway's on the gateway's. Inference sent straight to the Cortex REST API,
  not through the gateway, is in the totals but is put down to no one: no view says whose it was.

Snowflake meters AI in **credits**. The rows are priced one of two ways, and are **estimated** either way, because
the bill settles at month end:

1. At the **Credit price** on the connection, in its **Currency** (US dollars unless set). Set it on the connect form,
   or later under **Usage and spend** on the account's row.
2. Without one, at the organization's **rate sheet** (`ORGANIZATION_USAGE.RATE_SHEET_DAILY`): each day's effective
   rate after contract discounts. The read role needs the `SNOWFLAKE.ORGANIZATION_BILLING_VIEWER` database role for
   it, which the setup script does not grant, or the connection must be the organization account.

Without either, spend shows **not set up** and asks for a credit price. Refused the warehouse or the views, it shows
**needs permission** and names the grant.

**Spend** > **Provider** > **Snowflake's own page** breaks the credits down by account, user, person and object (an
agent, an AI function, the AI Gateway, Cortex Code), and shows each agent's cost against how much it was used.

Reading usage and spend spends the warehouse's credits each time. The script creates the warehouse as `XSMALL`,
suspending after 60 seconds. A longer interval under **Settings** > **Spend schedule** spends fewer.

## Rotate a key

For a key-pair user, open the setup script (the **Setup** icon on the row) and select **Generate a new key for
OPENCONTROLLER_READ** (or the control user), then **Generate**. The old key stops working at once: run the script's
`ALTER USER … SET RSA_PUBLIC_KEY` line again before the next scan. A federation user has no key to rotate.

## Upgrade an existing connection

The setup script is written for the connection as it is now, and every statement in it can run again: `CREATE … IF
NOT EXISTS`, `ALTER` and `GRANT` change nothing that is already so. After you upgrade OpenController, open **Setup** on
the account's row, run the script again as **ACCOUNTADMIN**, and select **Verify**. That brings any connection up to
date, whatever release it was connected on.

If you grant by hand instead, pick the release the connection was made on. Each step below it says what that release
added and the statements to run. The statements name the default users; use your connection's own. The release you run
is at the foot of the console's sidebar.

  </div>

  <div className="oc-upgrade-step" data-release="0.204.1">
    **v0.204.1 added AI spend and usage, and the Cortex AI Gateway**: what the account's AI credits cost and whose
    they were, how much each object is used, and who sends what through the gateway. Three things:

    1. **A warehouse**, if the connection has none. Name one under **Usage and spend** on the account's row, then run the
       script again. It creates the warehouse and grants `USAGE` on it:

       ```sql
       CREATE WAREHOUSE IF NOT EXISTS OPENCONTROLLER_WH WAREHOUSE_SIZE = XSMALL AUTO_SUSPEND = 60 AUTO_RESUME = TRUE INITIALLY_SUSPENDED = TRUE;
       GRANT USAGE ON WAREHOUSE OPENCONTROLLER_WH TO ROLE OPENCONTROLLER_READ;
       ```

    2. **A price for the credits**: the **Credit price** under **Usage and spend**, or let spend read the organization's
       rate sheet:

       ```sql
       GRANT DATABASE ROLE SNOWFLAKE.ORGANIZATION_BILLING_VIEWER TO ROLE OPENCONTROLLER_READ;
       ```

    3. **The gateway's use**, on an account with the Cortex AI Gateway:

       ```sql
       GRANT MONITOR ON AI GATEWAY SNOWFLAKE TO ROLE OPENCONTROLLER_READ;
       ```

       Without it, the gateway is listed and shows `usage_error`. An account without a gateway needs nothing: the
       script wraps the grant so it does not stop there.

    The `SNOWFLAKE.USAGE_VIEWER` role the views need is in every release's setup script already.
  </div>
</div>

## Permissions it uses

The setup script first runs `ALTER ACCOUNT SET FEATURE_RBAC_INHERITED_GRANTS = 'ENABLED'`, so one set of grants covers
every database. Each user gets a role of the same name, `TYPE = SERVICE`, that role as its default and no secondary
roles.

### Read role

| Grant | What it allows |
|---|---|
| `INHERITED USAGE ON ALL DATABASES IN ACCOUNT`, `INHERITED USAGE ON ALL SCHEMAS IN ACCOUNT` | Reach the objects in every database and schema. |
| `INHERITED MONITOR ON ALL AGENTS IN ACCOUNT` | The full agent spec and its grants, never the right to run one. |
| `INHERITED USAGE ON ALL MCP SERVERS IN ACCOUNT` | Lists a server's tools. Calling one is refused without rights on what it wraps. |
| `INHERITED MONITOR ON ALL CORTEX SEARCH SERVICES IN ACCOUNT` | Lists them; never queries one. |
| `INHERITED REFERENCES ON ALL SEMANTIC VIEWS IN ACCOUNT` | Their structure, never their data. |
| `USAGE ON SNOWFLAKE INTELLIGENCE SNOWFLAKE_INTELLIGENCE_OBJECT_DEFAULT` | Which agents CoWork shows. Skip it if `SHOW SNOWFLAKE INTELLIGENCES` returns nothing. |
| `MONITOR ON AI GATEWAY SNOWFLAKE` | What goes through the Cortex AI Gateway. The script runs it inside a block that returns a note on an account with no gateway, so the rest of the script runs on. |
| `DATABASE ROLE SNOWFLAKE.USAGE_VIEWER`, `OBJECT_VIEWER`, `SECURITY_VIEWER`, `GOVERNANCE_VIEWER` | The account usage views: usage and spend. |
| `APPLICATION ROLE SNOWFLAKE.TRUST_CENTER_VIEWER` | Trust Center findings (granted, not read yet). |
| `USAGE` on the warehouse | Usage, spend and the **Account usage** check. The script creates the warehouse: `XSMALL`, suspends after 60 seconds. |
| With a separate control user: `USAGE` on `OPENCONTROLLER` and `OPENCONTROLLER.STATE`, `SELECT` on `BLOCK_SNAPSHOTS` | Read the block records. |

It never holds `OWNERSHIP`, `MODIFY`, `OPERATE`, `MANAGE GRANTS`, `APPLY`, `INSERT`, `UPDATE`, `DELETE`, any `CREATE`
privilege, an administrator role, or any other role; **Read only** fails if it does.

### Control role (optional)

| Grant | What it allows |
|---|---|
| `MANAGE GRANTS ON ACCOUNT` | Share, remove and block. |
| `INHERITED USAGE ON ALL DATABASES IN ACCOUNT`, `INHERITED USAGE ON ALL SCHEMAS IN ACCOUNT` | Reach every agent and MCP server. |
| `MODIFY ON SNOWFLAKE INTELLIGENCE SNOWFLAKE_INTELLIGENCE_OBJECT_DEFAULT` | Publish to CoWork. |
| `SELECT, INSERT, DELETE ON TABLE OPENCONTROLLER.STATE.BLOCK_SNAPSHOTS`, `USAGE` on its database and schema | Record and restore what a block took. The script creates the database, schema and table. |
| `APPLY ON TAG OPENCONTROLLER.STATE.BLOCK_OWNER` | Tag a blocked agent with its owner. |
| `USAGE` on the warehouse | Write the block records. |

It holds no grant on your tables, only on its own `BLOCK_SNAPSHOTS`. With **The read user, copied**, all of this goes to
the read role, and **Read only** then fails.

A key-pair user's private key is stored in your secrets manager; the API returns only the public key. Workload identity
federation stores nothing.

## Remove the integration

Removing it deletes the stored keys from your secrets manager and stops scans. Then drop what the script made in
Snowflake (use your own names if you changed them):

```sql
DROP USER OPENCONTROLLER_READ;
DROP ROLE OPENCONTROLLER_READ;
DROP WAREHOUSE OPENCONTROLLER_WH;   -- if the script created it
-- if control was on
DROP USER OPENCONTROLLER_CONTROL;
DROP ROLE OPENCONTROLLER_CONTROL;
DROP DATABASE OPENCONTROLLER;
```
