OpenController reads a **Claude Platform organization** (the Claude API, managed in the Claude Console) with an
**Admin API key**, and a **Claude Enterprise organization** (claude.ai) with keys made in claude.ai. One integration
is one organization of each, or of either. It only reads: it never creates, changes or revokes anything, and never
calls a model. Individual accounts have no Admin API.

## What it unlocks

- **[AI Inventory](/discover/ai-inventory):** each Claude model called in the last 30 days, with its tokens, service
  tiers, the workspaces it was called from and how many API keys called it; each active API key, with its workspace,
  who created it, its status, expiry, key hint and 30-day tokens; and which key called which model.
- **[Spend](/discover/people-and-spend):** what each workspace was billed each day, by line item (tokens, web search,
  code execution, session usage), and each person's Claude Code use.
- **For Claude Enterprise, the [AI Inventory](/discover/ai-inventory)** too: members and groups; plugins, their MCP
  servers and marketplaces, with how each is installed and its content scan; the custom roles and what each grants, by
  feature, admin permission and connector; the connectors and projects people used; the models called in the last 30
  days, and who called them; and Claude in Slack, workspace by workspace and channel by channel. **[Spend](/discover/people-and-spend)** reads the organization's bill by day, surface (chat, Claude Code,
  Cowork, Claude in Slack), model and line, each member's share of it, and a seat per member with when they last used
  Claude. See [Connect Claude Enterprise](#connect-claude-enterprise).

To call Claude models through the [LLM gateway](/secure/gateway-overview), add Anthropic as a gateway provider instead
([Providers and routing](/secure/routing-and-mcp)).

## Connect an Anthropic organization

<Steps>
  <Step title="Create an Admin API key">
    In the [Claude Console](https://console.anthropic.com), as an **organization admin** (only admins can create one),
    go to **Settings** > **Admin keys** > **Create admin key**, and name it `opencontroller`. Copy the key: it starts
    with `sk-ant-admin`, and the Console shows it once. Then copy the organization ID (a GUID) from **Settings** >
    **Organization**.

    A workspace API key is refused at **Verify**: it cannot read the organization. A key linked to a service account
    with the admin role works too, and is the one that reads Managed Agents. Both begin `sk-ant-api…`, so the prefix
    does not tell them apart; the Console's API keys page names the key's owner.
  </Step>
  <Step title="Connect it">
    Go to **Integrations** > **Connect** > **Anthropic organization**. Fill in **Name**, **Organization ID** and **Admin
    API key**, and select **Connect**. The key goes to your secrets manager and cannot be read back.

    The **What opencontroller reads in …** dialog lists what the key reads. It needs no grants of its own. Select
    **Done**.
  </Step>
  <Step title="Verify">
    On the row, select **Verify**. The **Access** badge reads **Verified** when every check passes.

    | Check | Passes when |
    |---|---|
    | **Sign in** | The key is accepted and belongs to the organization you named. Shows its name and ID. |
    | **Members**, **Workspaces**, **API keys** | Each is listed; the check shows how many (active keys only). |
    | **Usage and cost** | Yesterday's usage and cost reports can be read. |
    | **Managed Agents** | The key reads Managed Agents in every workspace. An Admin API key acts in no workspace and reads none, which the check says; a service account key reads them. |
    | **Claude Code analytics** | Yesterday's Claude Code report can be read. |

    Scans run every 5 minutes by default, and read the last 30 days of usage; a model nobody called for 30 days is
    retired. Spend is read after a scan, at most every 6 hours, for the last 35 days.
  </Step>
</Steps>

## Connect Claude Enterprise

A connection reaches a Claude Enterprise organization with or without the Console. In the form, choose **Claude
Enterprise** (or both) under what the organization uses.

<Steps>
  <Step title="Create the read key">
    In claude.ai, as the **Primary Owner**, go to **Organization settings** > **API** > **Create key**, name it
    `opencontroller-read`, and give it the read scopes: `read:members`, `read:rbac_groups`, `read:plugins`,
    `read:claude_tag`, `read:analytics`, `read:compliance_activities`, `read:spend_limits`. The key starts with
    `sk-ant-api01`, and is shown once. Enable the Analytics API for the organization on the same page.

    `read:rbac_groups` is only on a key made for **all linked organizations**: a key made for one organization reads
    everything but groups. An organization without Claude in Slack need not grant `read:claude_tag`.
  </Step>
  <Step title="Connect it">
    Fill in the Enterprise **Organization ID** (under **Organization settings** > **Organization**) and the **Read
    key**, and select **Connect**. The key goes to your secrets manager and cannot be read back.
  </Step>
  <Step title="Verify">
    Verify signs in with the key, confirms the organization where the API says whose key it is, and tries one read per
    scope: members, groups, plugins, Claude in Slack, analytics, usage and cost, compliance activity and spend limits.
    A missing scope is named, with the scopes the key has. **Groups**, **Claude in Slack**, **Usage and cost** and
    **Compliance activity** are optional: a note says why a key may lack each, and the connection still verifies.
  </Step>
</Steps>

### What a scan reads

Eight sources, each a scope the key may lack on its own, so a key without groups still leaves the members reported.

| In Claude Enterprise | In the inventory |
|---|---|
| Members: email, name, role, when added | Identities (type `user`). |
| Groups, made in claude.ai or by SCIM, with the custom roles they grant | Identities (type `group`) that **contain** their members and **grant** their roles. A group whose roles the API could not read for the moment is read again before it is reported. |
| Custom roles, made in claude.ai or by Anthropic, and what each grants | Identities (type `role`): the product features its holders may use (`chat`, `claude_code`…), or a blanket grant of every feature (`all`) or every generally available one (`all_ga`); the admin-panel permissions (`permission_…`); and what may be done with connectors, each connector tool with its action, and how many of a connector's OAuth scopes the role may be given. A `managed` member's permissions are those of the roles their groups grant. Roles are read with `read:members`, so a key made for one organization reads them, where it cannot read groups. |
| Plugins: description, version, marketplace, served and latest version, components, reach, content scan, who made them (a member or an Admin API key), and how the organization and each group install them | Skills. How the organization installs one is its status (`required`, `auto_install`, `available`, `not_available`); only `not_available` keeps it from everyone, and each group allowed it **can use** it. Each MCP server among its components is an MCP server the plugin **contains**; its marketplace, the organization's or a member's personal one, is a registry that **contains** it, with how its last synchronization from its repository went. |
| Connectors and projects, as of the latest day the analytics have | MCP servers and knowledge bases, with that day and how many people used them. The analytics run a day or two behind; a scan reads one day, the latest the API has. A count the analytics cannot state (a breakdown not enabled for the organization) is left out, not written as 0. |
| The models called over the last 30 days, from the usage analytics | Models, with their tokens and requests over the window, the surfaces they were called from (`chat`, `claude_code`, `cowork`, `claude_tag`…), how many members called them, and each member who did, who **uses** them. Claude Code run through Amazon Bedrock is not in the analytics. |
| Claude in Slack: each Slack workspace and channel it is set up in | Agents: on or off, what they do while a Slack guest is in the channel (the guest policy: `allow`, `channel_only` or `restrict`, which applies when none is set), how they take part in a channel (the reply mode), their model, their environment, and the level each setting comes from. Instructions are not kept. |

### What Spend reads

Three sources, with `read:analytics` and the Analytics API enabled for the organization, and `read:members` for the
seats:

| Source | What it reads |
|---|---|
| **Claude Enterprise bill** | Each day's cost by surface, model and line, from the cost analytics. The service is the surface (Claude chat, Claude Code, Cowork, Claude in Slack…) and the meter the line: a token type, web searches, code execution or session usage. The amounts are the cost after discounts and before any credits, in US dollars: on a plan that buys credits up front, what the credits were spent on. **Billed** rows, under the account `Claude Enterprise`. |
| **Claude Enterprise bill by person** | Each member's cost by day, surface and model. **Attributed** rows: already in the bill, they never add to a total, and they put it down to the member by email. Cost no member is behind stays the organization's; a member who has left is named by address. |
| **Claude Enterprise seats** | One seat per member (SKU `claude_enterprise`, "Claude Enterprise seat"), with when they last used Claude in any surface, from the usage analytics. Set the seat's monthly price in Spend, as for other licences; **People** then shows each member's seat, their use, and who has been idle for 30 days. |

The analytics begin on 2026-01-01, run a few hours behind, and can be revised for about a week after a month ends.
A plan bought through AWS Marketplace is billed by AWS, monthly in arrears, at the same rates: the bill read here is
what that invoice adds up.

To change the keys, remove the connection and connect it again.

## Permissions it uses

An Admin API key reads the whole organization; there is no narrower one. OpenController calls only these endpoints, all
`GET`, on `https://api.anthropic.com`:

| Endpoint | What for |
|---|---|
| `/v1/organizations/me` | Sign in: proves the key, and refuses it if it belongs to another organization. |
| `/v1/organizations/users` | Members' emails, to name who created each API key. |
| `/v1/organizations/workspaces` | Workspace names (archived ones left out). |
| `/v1/organizations/api_keys` | Active API keys for the inventory; keys of every status for Claude Code, to put use through a key down to whoever created it. |
| `/v1/organizations/usage_report/messages` | Tokens by day, model, workspace and API key: the models in use. |
| `/v1/organizations/cost_report` | The bill by day, workspace and line item. |
| `/v1/organizations/usage_report/claude_code` | Claude Code use by person or API key, one day per request. |

With an Enterprise key, by its scopes: `/v1/organizations/users`, `/rbac_groups` (each group's `/members`, and a group
again when its roles were not available), `/rbac_roles` (and each role's `/permissions`), `/plugins` (and each plugin's `/installation_settings`), `/plugin_marketplaces`, `/analytics/connectors`, `/analytics/apps/chat/projects`,
`/claude_tag/slack_workspaces` and `/claude_tag/slack_channels`, `/analytics/usage` and `/analytics/cost` (the bill, the
seats' activity and the models in use), and for Verify one read each of `/analytics/summaries`,
`/spend_limits/effective` and `/v1/compliance/activities`.

<Warning>
An Admin API key can also change the organization: invite and remove members, create workspaces, change API keys.
OpenController only reads with it. Treat it as an administrator credential.
</Warning>

OpenController never calls a model, reads prompts or responses, or sees an API key's secret (the API returns only a
partial hint). From Claude Enterprise it never reads conversations, projects' files or Claude in Slack's
instructions.

**Spend rows.** Cost report rows are **billed**, in US dollars. Claude Code rows are **attributed**: they say whose the
use was, at its estimated cost, and never add to a total, because that cost is already in the API bill or covered by a
subscription. Use through an API key goes to the member who created the key; when two members' keys share a name, it
goes to no one.

On Anthropic's own page, Claude Code use through a subscription is its own line, **Claude Code subscriptions, outside
the bill**, with its amount: in the Overview's figures, under the **Where it went** treemap and on the **Breakdown**
tab. It is use put down to people that the Console bill has no line for, so it has no share of the bill. **Put down to
keys and people** and **Not put down to anyone** are of the bill's services only, Claude API and Web search.

## Change the key

When the connection cannot sign in, the **Integrations** page shows **Update the key**. Create a new Admin API key in
the Claude Console, paste it there, then delete the old one in the Console. The new key is verified at once.

## Remove the integration

On **Integrations**, select the bin icon on the row, then confirm. The stored key is deleted and scans stop; what was
discovered stays until later scans retire it. The key itself still works: delete it under **Settings** > **Admin keys**
in the Claude Console.
