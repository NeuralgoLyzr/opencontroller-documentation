## Asset

Anything AI-related that OpenController discovers on a connected platform. An agent is one kind of asset; the rest
are what agents use. The inventory's **All assets** tab shows every kind:

| Kind | What it is |
|---|---|
| Agent | A deployed agent, assistant or app that calls a model and acts: a Copilot Studio agent, a Bedrock agent, a Vertex AI agent, a Cortex Agent, a Genie space. |
| Model | A model deployment or an available model an agent calls. |
| MCP server | A Model Context Protocol server an agent connects to, hosted by the platform or external. |
| Tool | A function, connector or action an agent can call. |
| Skill | A packaged capability attached to an agent. |
| Identity | The service principal, role, key or workload identity an agent runs as. |
| Memory | A memory store or memory bank an agent reads and writes. |
| Code interpreter | A sandbox an agent runs code in. |
| Knowledge base | A data store or index an agent retrieves from. |
| Credential provider | A store an agent takes credentials from. |
| Guardrail | A guardrail configured on the platform, in front of an agent. |
| Gateway, endpoint | A gateway or endpoint through which an agent is reached. |
| Registry, registry record | An agent registry on the platform and the records in it. |
| Policy engine | A policy service the agent's platform consults. |
| Browser | A hosted browser an agent drives. |
| Artifact | A file or output an agent produced or depends on. |

Each asset records which connection found it, which account and region it lives in, and its relationships: which
agent uses which model, tool, server or identity. That is what the map draws.

## Agent

The asset kind that acts. OpenController governs agents; the other kinds give context about what an agent can
reach. The inventory's **Agents** tab lists agents alone, with their platform, type, account, region, platform
status and registry state.

## Connection

A platform OpenController reads: an AWS account, a Microsoft tenant, a Google Cloud project, a Databricks workspace,
an Anthropic organization, a Snowflake account. Every connection has a **read credential** for discovery, and may
have a **control credential** for actions. The read credential is enough for discovery, governance and posture.

## Scan

One pass of discovery over one connection. A scan lists the connection's assets and relationships, records what
changed, and reports what it could not read. Scans run on a schedule and on demand.

## Registry state

Where an asset stands with the organization:

| State | Meaning |
|---|---|
| **Shadow** | Discovered, and nobody has registered it. |
| **Awaiting approval** | A registration request is waiting for an approver. |
| **Registered** | Approved, with an owner, in the registry. |
| **Unmanaged** | On a platform where OpenController lists it for visibility only. |

A request can also end **rejected**, be **withdrawn** by the requester, or be **revoked** later by an approver, which
returns the asset to shadow.

## Owner

The person responsible for an agent. Discovery records who the platform names as the creator or owner, and that
prefills the owner when you register. The **People** page lists everyone discovery has seen.

## Policy

**Policies** is the registration policy: which asset kinds must be registered, and so count as shadow until they
are, what a request must state, and what an approval needs. **Security policies**, under Posture, are different:
they check configuration and raise findings, and a registration is checked against them.

## Finding

A risky configuration detected in the inventory by a security policy: an agent without an owner, a tool reaching a
sensitive store, a public endpoint. Findings map to the frameworks you choose.

## Module

A part of the product that can be turned on or off per installation. Discover, Register, Control, Posture and the
assistant are the core. The LLM gateway, Guardrails, Observability, Evals and Fine-tuning are modules that connect to a
service of their own. An installation runs a profile: `discover`, `govern` (adds Control) or `full` (adds every
module). The sidebar only shows the sections the profile includes.

## Roles

Each person holds one role: **Viewer**, **Operator**, **Admin** or **Owner**. Each role includes the ones before it.
Viewers read the inventory, the registry, findings and scans. Operators also run scans, request registrations,
try guardrails and change agent sharing. Admins also decide approvals, change the registry policy, make guardrails,
see violations, and add, change and remove connections and their credentials. Owners also manage single sign-on,
the access rules and who holds which role. Automation signs in with a service-account key that
carries a role of its own.
