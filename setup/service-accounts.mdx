A service account is a non-human caller: a script, a pipeline or another service that calls the API as itself. It holds one role, and signs in with a key. It is never an owner, and it never gets the default role: it has only the role it was given. The audit log marks what a service account did as a service's.

**Settings → Service accounts** lists them. Reading the list needs `service-accounts:read` and changing it `service-accounts:write`, both held by the Admin role.

## Create a service account

<Steps>
  <Step title="Open the form">
    On **Settings → Service accounts**, click **New service account**.
  </Step>
  <Step title="Name it and give it a role">
    - **Name**: 2 to 63 lowercase letters, digits and dashes, such as `ci-pipeline`. It names the caller in the audit log.
    - **Description** (optional).
    - **Role**: **Viewer**, **Operator**, **Admin**, or one of your organization's own roles. **Owner** is not offered.
  </Step>
  <Step title="Create">
    Click **Create**. The account has no keys until you mint one.
  </Step>
</Steps>

Make one service account for each machine, so the audit log says which one acted and a key can be revoked without stopping the others.

## Mint a key

<Steps>
  <Step title="Open its keys">
    On the row, click the **keys** button, or **Manage keys** in the row's menu. The dialog lists each key's hint, when it was created and by whom, and when it was last used.
  </Step>
  <Step title="Mint">
    Click **Mint key**. A dialog titled **Shown exactly once** shows the key with a copy button. Store it now: the key is SHA-256-hashed at rest and cannot be recovered later. Click **I stored it** when it is safe.
  </Step>
</Steps>

To replace a key, mint a new one, move the caller to it, then revoke the old one. A disabled service account cannot mint a key; enable it first.

## Use a key

A key has the form `cpk_<key id>_<secret>`. Send it as a bearer token:

```bash
curl -H "Authorization: Bearer cpk_<key id>_<secret>" https://opencontroller.example.com/v1/me
```

The answer names the service account, its role and its permissions, with `"service": true`. A person can also paste a key under **API credential** on the sign-in page and click **Use credential**, for break-glass access; the key stays in that browser tab.

Every call needs the permission its route needs, and the service account's role must hold it. The console's pages name the permission each action needs.

## Revoke, disable, delete

| Action | Where | What it does |
|---|---|---|
| **Revoke** | In the keys dialog, on a key's row | The key stops working now. The row stays, marked **Revoked**. |
| **Role** | On the account's row | Changes the role every key signs in with. |
| **Disable** | In the row's menu | Every key stops working until you **Enable** the account again. |
| **Delete** | In the row's menu | Removes the account. Every key stops working at once. This cannot be undone. |

## Least privilege

A built-in role is often more than a machine needs: a pipeline that only sends traces needs `observability:send`, not everything the Operator role holds. Under **Settings → Roles**, an owner can add a role of the organization's own that holds just the permissions the machine uses, and give it to the service account. See [Your organization's own roles](/administration/roles#your-organizations-own-roles).

## Static API keys

Static API keys are keys written into the secret `platform/api-keys`, seeded once from `DISCOVERY_API_KEYS` and then managed under [**Settings → Secrets**](/setup/secrets). They sign in without a service account. Keep them for break-glass use: a service account's key can be revoked, disabled and seen to be last used, and a static key cannot.

The secret's value is `name:role=key`, comma-separated for several. The name identifies the caller in the audit log. The role is `viewer`, `operator`, `admin` or one of your organization's own, and `viewer` when left out. A static key can never hold `owner`, and only a role the person writing it could give a service account. Each key is at least 32 characters, such as the output of `openssl rand -hex 32`. A static key is sent the same way, as `Authorization: Bearer`, or in an `X-API-Key` header.

Changing `platform/api-keys` takes `secrets:sign-in`, which only the Owner role holds by default, because whoever writes it can sign in as anyone. A new value applies at once. **Settings → Authentication** counts the keys in use under **Static API keys**.

A tool with a client at your identity provider can sign in as a service with the provider's client-credentials grant instead. It is named by its client id and holds only the roles granted to it.
