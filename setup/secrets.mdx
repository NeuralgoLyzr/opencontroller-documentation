OpenController keeps every credential it holds in your organization's secrets manager, never in its own database in the clear. Values are write-only: an admin sets or rotates them under **Settings → Secrets**, the server reads them, and they are never returned, logged or shown again.

Reading the list needs `secrets:read` and changing it `secrets:write`, both held by the Admin role. The three secrets that decide who signs in take `secrets:sign-in`, held by the Owner role.

## What is kept

| Secret | Kind | Managed where | A new value applies |
|---|---|---|---|
| `platform/api-keys` | Platform | **Settings → Secrets**; seeded from `DISCOVERY_API_KEYS` | At once |
| `platform/assistant-gateway-key` | Platform | **Settings → Secrets**; seeded from `ASK_CTRL_GATEWAY_KEY` | At once |
| `platform/handoff-key` | Platform | **Settings → Secrets**; seeded from `DISCOVERY_HANDOFF_KEY` | On restart |
| `platform/scim-token` | Platform | **Settings → Secrets**; seeded from `DISCOVERY_SCIM_TOKEN` | At once |
| `platform/admin-password` | Platform | **Settings → Secrets**; seeded from `DISCOVERY_ADMIN_PASSWORD` | When the first administrator is created |
| `integrations/<connection id>/client-secret` | Integrations | The connection, on **Integrations** | On the next scan |
| `sso/saml-signing-key` | Single sign-on | **Settings → Single sign-on**; replaced by reconnecting | On reconnect |
| Module credentials | Modules | The module's page under **Settings** | |
| `custom/<name>` | Custom | **Settings → Secrets** | |

**Settings → Secrets** groups the list the same way: **Platform**, **Integrations**, **Single sign-on**, **Modules** and **Custom**. Integration, single sign-on and module secrets belong to what uses them. The page lists them and links to where they are managed, with **Open Integrations**, **Open Single sign-on** or **Open LLM Gateway**.

## Choose the store

`SECRETS_PROVIDER` names the secrets manager. The page shows which one is in use under **Kept in**, and whether it is **Reachable**.

| `SECRETS_PROVIDER` | Store | Settings | What the server needs |
|---|---|---|---|
| `vault` | HashiCorp Vault, KV v2 | `VAULT_ADDR`; `VAULT_K8S_ROLE` for Kubernetes auth, or `VAULT_TOKEN`; `VAULT_CACERT`, `VAULT_MOUNT` (`secret`), `VAULT_PATH_PREFIX` (`opencontroller`), `VAULT_NAMESPACE` | A policy on its own prefix, nothing else |
| `aws_secrets_manager` | AWS Secrets Manager | `SECRETS_AWS_REGION`, `SECRETS_PREFIX` (`opencontroller/`) | `secretsmanager:GetSecretValue`, `PutSecretValue`, `CreateSecret`, `TagResource`, `DeleteSecret` on secrets under the prefix, and `ListSecrets` |
| `azure_keyvault` | Azure Key Vault | `AZURE_KEYVAULT_URL` | Key Vault Secrets Officer, through a workload or managed identity |
| `gcp_secret_manager` | Google Secret Manager | `GCP_PROJECT`, `SECRETS_PREFIX` | Secret Manager Admin on the project, or a custom role with get, add version, create, delete and list, through workload identity |
| Unset | MongoDB, sealed with AES-256-GCM | `DISCOVERY_SECRET_KEY`: 32 random bytes, base64, from `openssl rand -base64 32` | Nothing beyond MongoDB |

- **Vault** keeps each secret at `<mount>/data/<prefix>/<name>`, with the value under `value`. Each set is a new KV version, and delete removes the metadata, so every version goes. On Kubernetes there is no static token: the pod signs in with its service account through Vault's Kubernetes auth method and renews its short-lived token itself. TLS is verified against `VAULT_CACERT`.
- **AWS Secrets Manager** names start with `SECRETS_PREFIX`, so the IAM policy can be scoped to them. Secrets are tagged `managed-by=opencontroller` and deleted without a recovery window.
- **Azure Key Vault** names allow only letters, digits and dashes, so `custom/my_key` is stored as `oc-custom--my-u-key`. Deleted secrets are purged where purge protection allows it.
- **Google Secret Manager** ids are `SECRETS_PREFIX` plus the name, with `/` written as `__`. The secrets are labelled `managed-by=opencontroller`.
- **MongoDB, sealed** is for evaluation and single-node installs. The page says so, and asks you to point `SECRETS_PROVIDER` at your secrets manager for production. Changing `DISCOVERY_SECRET_KEY` makes every secret sealed with it unreadable.

Without `SECRETS_PROVIDER` or `DISCOVERY_SECRET_KEY`, the page shows **No secrets manager**. Nothing can be stored, the platform secrets are read from their environment variables, and integrations that need a client secret cannot be added.

<Note>
Moving from MongoDB to a secrets manager moves every sealed value into it once, at start. A value the manager already has is kept. Each move shows in **Activity** as **Moved in**, and the MongoDB copy is removed.
</Note>

`MONGO_URI`, `DISCOVERY_SECRET_KEY` and the store's own credential stay in the environment: they are what the server needs to reach the store at all.

## The list

Each row shows the **Secret** by name and its description. A platform secret's row also says which variable seeded it, and whether a new value applies at once or on the next restart. The other columns are **Used by**, **Version** (or **Not set**) and **Last set**, with who set it.

| Control | What it does |
|---|---|
| **New secret** | Adds a custom secret. Unavailable with no secrets manager. |
| **Set** | On an unset platform secret: stores its first value. |
| **Rotate value** | Stores a new version. Whatever uses the secret reads the new value; the old one is no longer used. |
| **Describe** | On a custom secret: changes its description, which admins see. |
| **Delete** | Removes every version from the secrets manager. What used the secret stops working until it is set again. This cannot be undone. |

Integration and single sign-on secrets cannot be rotated or deleted here. Change them on the connection, or by reconnecting single sign-on.

## Add a custom secret

Keep a credential here once, under `custom/`, and rotate it in one place.

<Steps>
  <Step title="Open the form">
    On **Settings → Secrets**, click **New secret**.
  </Step>
  <Step title="Name and value">
    - **Name**: kept as `custom/<name>`. Letters, digits, `-` and `_`, with `/` to nest, such as `evals/openai-api-key`. A name that already exists is refused.
    - **Value**: write-only. It can be rotated or deleted, never read back.
    - **Description** (optional): what it is for.
  </Step>
  <Step title="Save">
    Click **Save secret**. The row appears under **Custom** at version 1.
  </Step>
</Steps>

## Rotate a secret

In the row's menu, click **Rotate value**, enter the **New value** and click **Rotate**. The version goes up by one. A platform secret marked as applying on the next restart keeps using the old value until OpenController restarts; every other secret is in use at once.

## Platform secrets

Platform secrets are keys OpenController itself uses. Each is seeded once. On first start, a platform secret whose environment variable is set is stored in the secrets manager. From then on the stored value is the one used. The variable can then be removed. If the two differ, the server's log says so, and the stored value still wins.

| Secret | Seeded from | Used by | Applies |
|---|---|---|---|
| `platform/api-keys` | `DISCOVERY_API_KEYS` | API authentication: static keys, `name:role=key`, comma-separated. See [Static API keys](/setup/service-accounts#static-api-keys). | At once |
| `platform/assistant-gateway-key` | `ASK_CTRL_GATEWAY_KEY` | The assistant: the LLM gateway's key its model calls carry, when the gateway asks for one. | At once |
| `platform/handoff-key` | `DISCOVERY_HANDOFF_KEY` | The sign-in hand-off from the control plane that created the organization. The variable's value wins over the stored one, so the cell always agrees with the control plane. | On restart |
| `platform/scim-token` | `DISCOVERY_SCIM_TOKEN` | SCIM provisioning: the bearer token your identity provider sends. | At once |
| `platform/admin-password` | `DISCOVERY_ADMIN_PASSWORD` | The first administrator, used once when that account is created. | When the first administrator is created |

<Warning>
`platform/api-keys`, `platform/handoff-key` and `platform/scim-token` decide who signs in, and as what: whoever sets them can sign in as anyone. Changing or deleting them takes `secrets:sign-in`, which only the Owner role holds by default.
</Warning>

## Activity

The **Activity** section at the foot of the page lists the latest changes. Each row shows **When**, the **Change** (**Created**, **Rotated** with the version, **Described**, **Deleted** or **Moved in**), the **Secret** and **By**. Values are never recorded. Every change to a secret is kept, who made it and when.
