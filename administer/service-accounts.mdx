Each app gets its own identity: its key works only with the account's role, every call it makes is recorded under its name, and you can revoke it without touching anyone else. Each key looks like `cpk_<key id>_<secret>`.

## Choose the least role

| The app needs to | Role |
|---|---|
| Read the inventory, findings and other data | **Viewer** |
| Also run scans, or send traces to Observability | **Operator** |
| Also change integrations, keys or settings | **Admin** |

A service account can never be **Owner**. If no built-in role fits, an **Owner** can make a custom role with only the permissions the app needs, for example only `observability:send`. See [Make a custom role](/administer/members-roles-teams#make-a-custom-role).

## Create the account and its key

In **Settings** > **Service accounts**, select **New service account**. The **Name** takes lowercase letters, digits and dashes, for example `ci-pipeline`. **Role** defaults to **Viewer**. A new account has no keys: open its keys and select **Mint key**.

<Warning>The key is shown once. It is stored only as a SHA-256 hash and cannot be recovered. Paste it straight into your app's secret store, for example as the CI secret `OC_API_KEY`, never into chat, tickets, code or logs. If you lose it or it is exposed, revoke it and mint a new one.</Warning>

## Call the API with the key

Send the key as a bearer token. First, check who the key signs in as:

<CodeGroup>
```bash curl
curl -s https://console.example.com/v1/me \
  -H "Authorization: Bearer $OC_API_KEY"
```

```python Python
import os, requests

r = requests.get(
    "https://console.example.com/v1/me",
    headers={"Authorization": f"Bearer {os.environ['OC_API_KEY']}"},
    timeout=30,
)
r.raise_for_status()
print(r.json())
```

```typescript TypeScript
const r = await fetch("https://console.example.com/v1/me", {
  headers: { Authorization: `Bearer ${process.env.OC_API_KEY}` },
})
if (!r.ok) throw new Error(`${r.status} ${await r.text()}`)
console.log(await r.json())
```
</CodeGroup>

The answer names the account and its role, with `"method": "service_key"` and `"service": true`:

```json
{
  "name": "ci-pipeline",
  "method": "service_key",
  "role": "operator",
  "permissions": ["assets:read", "scans:run", "…"],
  "service": true,
  "org_id": "org_1a2b3c"
}
```

Then do the app's real work. This starts a scan of the connected AWS accounts:

```bash
curl -s https://console.example.com/v1/scans \
  -H "Authorization: Bearer $OC_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"provider":"aws"}'
```

And this reads the first page of discovered agents:

```bash
curl -s "https://console.example.com/v1/assets?kind=agent&limit=50" \
  -H "Authorization: Bearer $OC_API_KEY"
```

Errors come back as `application/problem+json`, with a `code` to branch on and a `request_id` to quote to support.

## Where else keys are used

- **Sending traces**: the key goes as `x-api-key`. The account needs `observability:send`, which **Operator** holds. See [Send traces](/monitor/send-traces).
- **Guardrails**: an app or Claude Code checks text with a key whose role holds `guardrails:test`. See [Use guardrails in any app or Claude Code](/secure/guardrails/use-anywhere).
- **The console**: paste a key in **API credential** on the sign-in page, for automation and break-glass access.

## Check what the app did

**Last used** on the key shows when it was last used. In **Settings** > **Audit log** > **Identity & access**, the account shows as `service_account.created` and its key as `key.minted`, and changes the app makes to people, keys or settings show `ci-pipeline (service)` as **Who**. ## Rotate, revoke and disable

Rotate a key on a schedule, and whenever someone who saw it leaves. Both keys work until you revoke the old one, so the app never breaks:

1. Select **Mint key** a second time. The old key keeps working.
2. Put the new key in the app's secret store and run the app once.
3. Select **Revoke** on the old key. It stops working at once.

- Changing the account's **Role** applies to every key at once.
- **Disable** stops every key until you enable the account again. You cannot mint a key while it is disabled.
- **Delete** stops every key at once. This cannot be undone.
- The **Key** column shows only the key id and the last four characters. The full key is never shown again.

<Info>OpenController makes some service accounts for itself, for example `guardrails-platform` and `guardrails-gateway` for the guardrail engine. If you revoke their keys or remove them, OpenController makes them again on next use.</Info>

## Who can use it

- **Admin** creates accounts and mints, rotates and revokes keys.
- Giving an account a custom role also needs an **Owner**.
